## 1. 业务背景与目标

商家需要引入更多外部应用处理运营、身份认证、配送与支付，同时继续处理已有订单和资产。本轮升级要解决的核心问题是：应用能力和故障对商家不够可见；密码登录缺少按人群限制；库存可售性与配送区域耦合；外部运费缓存缺少经营侧控制；礼品卡资金记录未进入统一交易体系；内容、搜索和通知链路存在兼容及可靠性缺口。

本次以提供的 Base 为事实依据。核心后端 `pyproject.toml` 标注 3.22.0，Dashboard `package.json` 标注 3.22.2；平台配置使用后端 3.22 镜像及 Dashboard `latest`。版本标签不等于实际部署证明。调研为源码、配置和测试静态阅读，未获得真实商家访谈、生产数据、调用日志或运行实例，不能据此推断存量规模、采用率、故障率或收益。文中用户任务及功能边界是根据业务输入和现有系统提出的产品决策。

目标与成功判定：

## 3. 需求条目

#### 应用扩展与故障管理

### R01 · 扩大应用挂载能力并统一 Dashboard 体验

- 来源：Instruction“支持更多外部应用接入”“改善商家对应用扩展和故障的管理”；推导依据：Base 已有 `POPUP`、`APP_PAGE`、`NEW_TAB`、`WIDGET`，但 `app/types.py` 与 `app/manifest_validations.py` 的详情 Widget 仅覆盖七类对象，Dashboard 的 `extensions/extensionMountPoints.ts` 也有相同缺口。
- 优先级：P0
- 需求描述：保留全部现有挂载点、目标类型及默认 `POPUP` 行为；补齐分类、页面/模型、页面类型/模型类型、菜单和促销详情的 `WIDGET`，分别与这些对象现有“更多操作”入口配套。界面文案沿用 Dashboard 对 Page/Model 的既有称呼，API 仍使用 `Page`、`PageType`。Manifest 能声明标签、地址、权限、挂载位置及适用的 GET/POST 选项；非法位置与目标组合在安装/更新时返回字段错误且不部分替换已安装扩展。详情传递对象 ID，已有列表入口继续传递选中 ID；有渠道上下文时传递当前渠道，不附带无关个人或订单数据。应用和员工均拥有所需权限才可启动扩展。停用/卸载、权限撤回后入口与令牌访问同步失效；扩展失败不能阻断原生页面操作。新能力在 `apps` 与 `extensions` 路由/开关可达路径中保持一致，避免重复入口。
- 验收条件：
  - AC-01-1：安装声明五类新增详情 Widget 的合法应用，分别打开对应详情页，显示标签及内容，并向应用传递当前对象的正确 ID；无对应扩展时不显示空容器。
  - AC-01-2：使用不含新字段的旧 Manifest 安装，并依次启动旧 `POPUP`、`APP_PAGE`、`NEW_TAB`、`WIDGET` 示例，默认目标、跳转与 GET/POST 交互保持原契约。
  - AC-01-3：提交不合法的挂载点/目标/URL/选项组合或超出应用授权的扩展权限，安装/更新失败，错误定位到扩展字段，原扩展集合及权限不变。
  - AC-01-4：员工缺少扩展所需权限时入口不可用；直接请求扩展令牌也被拒绝。撤权或停用应用后，重新访问不能再获得有效令牌或启动扩展。
  - AC-01-5：应用加载超时或 iframe 消息来源不匹配时，页面显示局部错误和重试入口，原生保存仍可操作；不向错误来源发送凭证，不在 URL 或日志中暴露长期 App token。

### R02 · 展示应用故障、熔断影响与恢复路径

- 来源：Instruction“改善商家对应用扩展和故障的管理”；推导依据：Base 已有 `App.breakerState`、`breakerLastStateChange`、投递记录与自动熔断，但 Dashboard 非生成代码未见熔断状态的消费。
- 优先级：P0
- 需求描述：应用列表、应用详情及全局应用提醒区区分安装失败、主动停用、Webhook 投递失败和熔断。显示最近状态变化时间、受影响的同步事件、最近失败原因与投递详情入口；区分“未启用熔断监控”“数据暂不可用”和“正常”，不能把无数据视为健康。沿用 Base 的 `CLOSED`、`OPEN`、`HALF_OPEN` 和部署级启用/观察模式：半开是恢复观察、允许请求通过，不宣称只放行一个探测请求。既有阈值作为首版默认，不新增商家自由调节阈值或强制清零按钮；恢复通过现有冷却和成功请求判断。商家可查看详情、按既有能力重试异步投递、停用/启用应用；同步资金动作不能从故障页盲目重放。对无权查看详细日志的员工只显示必要的受影响提示。平台允许先观察后启用阻断，升级不自动开启新的阻断策略。
- 验收条件：
  - AC-02-1：监控启用且应用进入 `OPEN` 时，列表和详情标注“同步调用已熔断”与时间、事件范围；未受监控事件及其他应用不被误标停用。
  - AC-02-2：模拟冷却后恢复和再次失败，页面按 API 显示 `HALF_OPEN` 后的 `CLOSED` 或 `OPEN`；沿用默认 5 分钟统计窗、初始失败至少 100 次且失败率至少 35%、冷却 2 分钟、恢复失败至少 20 次且失败率至少 30%、恢复成功至少 50 次的判定，边界有自动化验证。
  - AC-02-3：关闭熔断功能或只启用观察模式，页面分别显示未启用或仅观察，不把模拟熔断说成已阻断；请求实际是否发送与模式一致。
  - AC-02-4：应用停用、安装失败、异步投递失败各发生一次，显示不同状态及相应操作；重试异步投递新增尝试记录，不触发同步扣款或退款。
  - AC-02-5：有权限人员可见脱敏失败详情；无权限人员直接查询日志或操作应用被拒绝。日志不包含密码、完整礼品卡码或长期凭证；状态请求失败时显示未知并可刷新。

#### 登录与账号连续性

### R03 · 提供三种密码登录策略

- 来源：Instruction“支持全部用户使用密码、仅顾客使用密码及仅依赖外部身份等登录选择”；推导依据：Base `CreateToken.get_user` 校验凭据、确认状态与激活状态，尚无按用户类型选择密码登录模式。
- 优先级：P0
- 需求描述：提供实例级密码登录策略，产品语义为 `ALL`（所有用户可用密码）、`CUSTOMERS_ONLY`（仅非员工可用密码）、`DISABLED`（所有用户禁用密码）。由部署配置控制，Dashboard 设置页展示当前策略及切换说明，首版不提供在线修改按钮；匿名 `shop` 查询可获得策略及可用外部认证方式，不暴露账号存在性。新装与升级未配置时均为 `ALL`。模式限制本地密码认证，不限制已授权的应用 token、外部身份认证或匿名购物。后端统一执行策略，不能仅隐藏表单。员工登录页在后两种策略下不显示密码提交和找回密码入口；可用外部登录方式正常展示，无外部方式则明确提示联系管理员。配置查询失败不能默认显示并启用密码入口。保留停用账号、邮件确认、节流、CSRF 与既有权限校验。
- 验收条件：
  - AC-03-1：未设置策略的 Base 升级后，激活并满足确认条件的顾客和员工都可按原密码登录，原密码哈希不被改写。
  - AC-03-2：配置 `CUSTOMERS_ONLY`，顾客密码登录成功，员工及超级管理员的正确密码登录被拒绝且不签发 token，Dashboard 只提供可用外部登录；改变 audience 或直接调 API 不能绕过。
  - AC-03-3：配置 `DISABLED`，顾客和员工的所有本地密码登录请求均被拒绝；已配置外部认证与合法 App token 调用仍正常。
  - AC-03-4：未激活账号、错误密码、不存在账号及受限账号的公开响应不泄露额外身份信息；需要交互提示的策略禁用信息在无需查询指定邮箱的策略响应中可获得。
  - AC-03-5：传入未知部署配置值，启动/配置检查失败并指明合法值；策略查询超时的 Dashboard 显示重试状态，不提供绕过限制的密码表单。

### R04 · 限制覆盖账号生命周期并防止切换锁死

- 来源：Instruction“保护存量账号”“处理受影响的安全、兼容与数据迁移问题，并具备恢复”；推导依据：Base 的 `tokenRefresh`、外部刷新、密码重置和员工邀请为不同入口，只限制 `tokenCreate` 会留下绕过路径。
- 优先级：P0
- 需求描述：限制策略覆盖密码登录、密码设置/修改、重置邮件、带密码注册和员工密码邀请；被禁用人群不能借任一路径得到本地登录凭证。无密码顾客创建和外部身份注册可继续；含被禁止密码的写请求原子拒绝，不能先创建账号再报错。公开找回入口沿用防枚举响应，受限账号不发密码重置邮件，既有重置 token 不能恢复密码登录。切换至更严格策略时，受影响人群已签发的本地访问及刷新会话失效；无法区分来源的旧会话安全失效并要求重新登录，不清除账号、密码哈希、订单归属和外部身份关联。限制放宽后旧会话不复活，可重新用保留密码登录。员工升格为 `is_staff=true` 后立即受员工规则约束；外部身份不会仅因可控邮箱匹配而自动获得员工权限。
  切换前需要运维完成受影响账号清单、至少一个具有管理权限的外部账号实际登录、回调与刷新验证、无密码邀请指引和部署配置恢复演练。产品不另建身份提供方。外部服务故障不自动放宽策略；经授权的运维通过部署配置恢复 `ALL` 并记录操作。
- 验收条件：
  - AC-04-1：员工密码被禁用后使用旧重置链接、员工邀请链接、设置密码 mutation 或旧 refresh token，均不能获得可用本地会话；旧 access token 也无法继续访问受保护数据。
  - AC-04-2：在 `CUSTOMERS_ONLY` 下，顾客注册、重置及修改密码正常；在 `DISABLED` 下带密码注册被原子拒绝，而外部身份创建/登录按原规则成功。
  - AC-04-3：顾客登录后被设为员工，下一次受保护调用或刷新即应用员工策略；外部登录也仍受员工权限、激活状态限制。
  - AC-04-4：严格模式部署预检中找不到经过验证的外部管理员登录路径，预检判为不通过，交付检查不得宣称可上线；恢复原配置后保留账号可重新密码登录，历史订单和身份关联不变。
  - AC-04-5：禁用期间通过公开重置入口请求存在和不存在的邮箱，响应不可据此判断账号存在，受限账号无重置邮件；恢复密码模式也不会让禁用期间或切换前失效的会话重新有效。

#### 库存与外部运费

### R05 · 按渠道选择仓库库存规则

- 来源：Instruction“让库存管理更直接地遵循仓库与销售渠道的关系”“存量商家应能保留现有经营方式，再逐步切换”；推导依据：`WarehouseQueryset.for_country_and_channel` 同时依赖国家、配送区域与渠道关系，`for_channel` 已存在直接仓库关系。
- 优先级：P0
- 需求描述：新增渠道级库存模式“兼容配送区域”和“仅按渠道仓库”。升级及未指定的新建渠道默认为兼容模式；商家在渠道详情选择新模式，API 提供相同读写能力。新模式下仅从关联该渠道的仓库计算可售库存、库存校验、预留、订单分配及后续补货；配送地址国家和仓库是否关联配送区域不再决定库存来源。国家仍决定合法配送方式、税费和地址规则；有库存不等于可配送。可售数遵守在库减分配减有效预留、库存跟踪与预售原有规则，保留渠道仓库顺序/分配策略、自提本仓/全仓及私有仓规则，不放宽自提资格。共享仓库的真实存量不能按渠道复制。
  Dashboard 展示当前模式、关联仓库、顺序及切换影响，说明可能增加可售区域；旧模式继续显示配送区域关联要求。保存前展示变更摘要并要求执行人员确认。切换或解除仓库关联不释放、重分配或改写既有订单的有效分配；已有结账在下次报价、预留或完成时按新规则重新校验。未成交预留失效/释放策略须与重新校验一致，不能被重复扣减。无关联仓库时，跟踪库存且非预售商品不可购买。
- 验收条件：
  - AC-05-1：仓库关联渠道且有库存，但没有覆盖收货国家的配送区域，兼容模式保持 Base 不可售结果；切到新模式后可查到库存并分配，但缺少有效配送方式时仍不能完成需配送结账。
  - AC-05-2：仓库未关联当前渠道，即使关联了覆盖国家的配送区域，新模式也不能使用其库存；不同渠道查询结果符合各自仓库关联。
  - AC-05-3：两个渠道共享仅剩 1 件的仓库，并发提交各 1 件，最多一单成功分配，另一单返回可处理的库存不足；取消释放后可再次购买。
  - AC-05-4：切换模式或移除仓库关系后，已有订单分配、退货回库和履约仍指向原仓库；未完成结账重新校验后不足则明确报错，不能沿用过期可售数成交。
  - AC-05-5：新旧两种模式下分别运行本仓自提、全仓自提、预售和不跟踪库存场景，保留各自规则；私有仓不能因新模式直接成为顾客可见自提点。
  - AC-05-6：无渠道管理权限的员工不能保存模式；有权限人员保存并刷新后看到新模式及仓库顺序。未显式切换的存量渠道结果与升级前代表性样本一致。

### R06 · 控制外部运费调用与缓存

- 来源：Instruction“让外部运费计算更加可控”；推导依据：`WebhookPlugin.get_shipping_methods_for_checkout` 对 `SHIPPING_LIST_METHODS_FOR_CHECKOUT` 使用固定 12 小时缓存，另有结账与订单配送方式过滤事件。
- 优先级：P0
- 需求描述：在渠道配置中分别管理外部报价缓存有效期和外部过滤调用开关。报价 TTL 用秒，允许 0—86400，0 表示不使用报价缓存，未指定为 43200 秒以保留 Base；“执行外部配送方式过滤”默认开启，关闭时只跳过 `CHECKOUT_FILTER_SHIPPING_METHODS` 和 `ORDER_FILTER_SHIPPING_METHODS`，不关闭本地配送校验或外部报价来源。订单按所属渠道取配置。设置只影响运费链路，不改变税费/支付 Webhook。Dashboard 提供字段说明、校验和保存结果；关闭过滤前说明可能放行原先被应用排除的方式。
  缓存按应用/Webhook、渠道及影响报价的结账内容隔离。地址、商品/数量、金额/折扣、币种等变化，应用停用/更新，以及配置变化不能复用旧上下文报价；自定义 subscription 影响报价的数据也须纳入失效规则，不能只凭固定旧 payload 判定未变。失败、超时、无效响应不缓存为成功报价，合法空方式列表可以缓存。返回报价必须满足渠道币种、非负金额、有效标识及精度规则。未过期且上下文匹配的缓存可使用；过期报价不能因故障无限沿用。获取报价失败时保留仍合法的本地或其他应用方式，没有方式则返回可重试的不可配送结果，不能变成免费运费。过滤事件启用但失败/熔断时，受该过滤影响的候选方式暂不可用于成交；商家可显式关闭过滤恢复原候选方式。选中方式在完成结账前必须再确认其有效性，金额变化返回现有价格变更语义而非静默扣更多款。
- 验收条件：
  - AC-06-1：未显式配置的渠道，同一上下文在 43200 秒内复用合法外部报价；设置 TTL 为 0 后连续两次独立报价请求均调用应用；负值或超过 86400 的值被拒绝且原值不变。
  - AC-06-2：修改地址、数量、折扣、币种相关上下文或 subscription 选取的自定义报价数据，旧报价不再命中；不同渠道和应用的相同外部方式 ID 不串用缓存。
  - AC-06-3：关闭过滤后，结账和订单不再调用两个过滤事件，外部报价仍执行，本地重量、国家和价格限制仍生效；重新开启后恢复调用。
  - AC-06-4：应用超时、熔断或返回错误币种/负金额，界面/API 不展示该错误报价；无其他合法方式时无法完成结账，错误后重试会重新请求而非命中失败缓存。
  - AC-06-5：过滤启用时过滤服务失败，候选方式不会未经筛选成交；商家显式关闭后重新获取方式可恢复流程，已生成订单的运费快照不被重算。
  - AC-06-6：改变 TTL、过滤开关、停用报价应用或完成有效应用更新，下一次结账检查使用新配置；选中报价失效或涨价时返回可识别错误供消费者重新选择/确认。

#### 礼品卡、交易与退款

### R07 · 将礼品卡支付记入统一交易

- 来源：Instruction“将礼品卡纳入统一的交易与退款管理”；推导依据：Base `add_gift_cards_to_order` 独立扣减余额、关联订单并产生礼品卡事件，`TransactionItem` 尚无礼品卡来源关系。
- 优先级：P0
- 需求描述：成功使用礼品卡支付订单时，为每张实际扣款的卡建立平台管理的 `TransactionItem` 及成功扣款事件，能关联订单、礼品卡和原资金来源，显示掩码卡号与币种；外部应用不得冒充平台礼品卡交易。沿用现有结账添加/移除礼品卡入口和最终下单扣减时机，单纯添加卡、报价或失败结账不产生成功扣款。多卡按稳定顺序消耗，首版按礼品卡创建时间、ID 排序；每张扣款不超过有效余额及订单剩余应付。卡必须激活、未过期且币种一致。混合支付的支付应用仅处理扣除礼品卡后的剩余应付，礼品卡不作为折扣改变商品价格/税基；原折扣及税费计算仍按其规则执行。
  余额扣减、交易事件、订单归属和结账完成保持一致，重试同一结账返回同一订单与交易；跨结账并发不得超用余额。若外部资金已成功而礼品卡/库存校验失败，保留真实外部资金状态并进入明确的补偿或人工处理状态，不伪造订单成功、不重复扣款。统一订单实付汇总包含礼品卡一次，旧礼品卡补偿字段不能再被消费者作为第二次支付相加。
- 验收条件：
  - AC-07-1：订单应付 100 元，使用有效礼品卡 30 元和外部支付 70 元完成，卡余额减少 30 元，生成礼品卡成功交易 30 元，订单实付显示 100 元，支付应用只收到 70 元应付。
  - AC-07-2：两张卡分别有 40 元、80 元且按稳定顺序支付 100 元，分别扣 40 元、60 元并产生两笔交易；重复完成同一结账不增加订单、交易或扣款。
  - AC-07-3：添加礼品卡后移除、取消结账或库存校验失败，未成交卡余额不变、无成功扣款；卡过期、停用或币种不匹配时返回对应业务错误。
  - AC-07-4：余额 50 元的同一卡同时支付两个 40 元结账，最终总扣款不超过 50 元，失败方得到余额不足并可刷新，不出现负余额。
  - AC-07-5：全额礼品卡支付可按既有订单确认配置成交，无需生成虚构 PSP 交易；匿名或无权限人员查询时无法得到完整卡码、其他持卡人信息或非本人的交易。
  - AC-07-6：模拟外部支付已扣款后本地成单失败，真实资金记录可查询，礼品卡未重复扣减，重试或补偿操作有同一业务关联且不重复调用扣款。

### R08 · 统一处理礼品卡退款及混合退款

- 来源：Instruction“将礼品卡纳入统一的交易与退款管理”“保护已有交易、资产”；推导依据：已有 `transactionRequestAction`、`transactionRequestRefundForGrantedRefund`、退款原因与授权退款流程，礼品卡应复用其管理入口。
- 优先级：P0
- 需求描述：礼品卡成功扣款交易支持部分/全额 `REFUND`，退款回原卡，通过平台内部处理，不投递至第三方 PSP。每笔累计已退加处理中金额不超过该笔实扣；金额必须为正、符合币种精度，省略金额取剩余可退额。退款审批/授权与资金成功分开，只有余额恢复和成功交易事件同时确认才显示成功。Dashboard 在订单交易卡片及现有退款流程显示来源、实付、已退、处理中、剩余可退、退款原因及事件，并允许按原来源明确拆分混合退款；不同币种不混合相加。退货、取消订单与资金退款保持明确区分，取消不隐式重复退款。
  已过期或停用原卡允许原路退回余额，但保留原有效期与停用状态并提示“资金已退回、卡仍不可消费”；激活或改有效期属于礼品卡管理操作，不随退款自动发生。发生资金使用的卡不得因普通删除丢失余额与交易关联；删除应被阻止并引导停用。异常历史卡无法定位时退款失败且不自动转现金。业务退款申请须具备稳定幂等标识；重复提交和异步重试返回原结果。具有 `HANDLE_PAYMENTS` 的人员可退款；浏览订单需订单权限，单独修改礼品卡余额/状态仍需 `MANAGE_GIFT_CARD`，不能借退款创造任意余额。
- 验收条件：
  - AC-08-1：礼品卡交易实扣 30 元，退款 10 元成功，卡余额增加 10 元，交易已退为 10 元、剩余可退为 20 元，订单和礼品卡事件可互相追溯，PSP 未收到请求。
  - AC-08-2：针对同一申请重复提交退款，余额只恢复一次；同时申请两笔超过剩余可退额的退款，累计成功及处理中金额不超过实扣，超出部分被拒绝。
  - AC-08-3：对 30 元礼品卡加 70 元现金订单申请退款 50 元并明确拆为卡 20 元、现金 30 元，分别执行原路退款；现金失败时卡的真实成功保留，界面显示部分完成，重试只处理未成功部分。
  - AC-08-4：原卡已过期或停用，退款成功恢复余额但不改变到期日/状态，Dashboard 明确提示不可消费；尝试删除有资金交易的卡被阻止，仍可停用。
  - AC-08-5：零、负数、超精度、超过剩余额度及未扣款交易的退款请求返回字段级错误，无余额变化；无支付处理权限者即使能查看订单也不能提交。
  - AC-08-6：取消订单后重试退款或重复授权退款，系统按原申请记录处理，不产生额外资金返还；退款成功与退货回库各有独立状态。

### R09 · 对历史礼品卡账务迁移和对账

- 来源：Instruction“保持存量商家的日常业务连续”“保护存量……订单、交易……资产”；推导依据：历史扣款金额可存在礼品卡事件及订单补偿记录中，不能根据当前余额反推每笔订单支付。
- 优先级：P0
- 需求描述：升级前盘点历史 `Payment`、`TransactionItem`、礼品卡事件和订单补偿，区分已退款、未退款及证据不足记录。有可信订单扣款/退款证据的历史礼品卡建立仅用于账务归一的交易及迁移标识，不再次扣余额、不再次发消费/退款通知；订单总实付和总已退保持经济含义一致。`Payment` 与新交易并存时统一展示来源但不得把同一次支付映射成两笔可操作资金。迁移可分批、可续跑、可幂等重跑；迁移前后按币种校验卡余额、订单实付/已退和来源关联，保留审计映射。
  证据不足的历史记录保留只读旧账及明确“待核对”标识，不凭当前余额补造成功交易，不开放不确定金额的自动退款。由财务使用可追溯的线下证据录入经审核的账务映射；未完成核对不能宣称历史自动退款已覆盖。新支付统一记账从维护窗口后生效，不能在同一订单同时走两套礼品卡扣减逻辑。
- 验收条件：
  - AC-09-1：迁移包含旧卡支付、混合支付、已部分退款、零余额卡、停用/过期卡的样本，迁移后每张卡余额及每个订单净支付与迁移前证据一致，没有第二次资金动作或顾客通知。
  - AC-09-2：中断批次后续跑并完整重跑，生成交易数与第一次完整运行一致，来源映射无重复，已迁移退款额度不扩大。
  - AC-09-3：删除/缺失历史事件的样本被列入差异报告并显示旧账待核对，系统不虚构金额，也不提供可误执行的自动退款按钮。
  - AC-09-4：历史旧支付订单在 Dashboard 仍能查看原 PSP 参考号、事件与已退金额；订单汇总不将兼容字段和迁移交易重复相加，存量应用获得明确的字段口径迁移说明。

### R10 · 增加交易列表查询与财务定位入口

- 来源：Instruction“改善交易查询”；推导依据：Base `PaymentQueries` 有单个 `transaction(id/token)` 和旧 `payments`，没有统一的新交易分页列表，订单搜索还受已索引交易数量上限影响。
- 优先级：P0
- 需求描述：提供面向 `TransactionItem` 的分页列表查询，保留现有按 ID/token 的单笔查询。首版筛选包括交易 ID/token、交易及事件 PSP 参考号、订单/结账 ID、渠道、创建时间范围、来源应用和礼品卡来源；可组合条件按 AND，单字段多值按 OR。精确 ID/参考号查询不受订单全文索引数量上限影响，不把参考号当全局唯一。默认创建时间倒序并有唯一 ID 作稳定次序；支持游标前后分页，禁止无界导出。时间以 UTC 存储和筛选，Dashboard 按当前时区展示并注明边界。保留旧全局 ID 与 UUID token 的读取能力；金额分币种呈现。
  Dashboard 增加“交易”查询入口，可从结果进入订单/交易详情，并能在礼品卡详情查看其使用及退款交易。无关联订单的结账交易仍可查到并标注来源。列表、详情和筛选计数遵循相同服务端授权和渠道隔离；沿用 `HANDLE_PAYMENTS` 作为交易查询权限，订单深链另行校验订单权限，不扩张应用现有访问边界。
- 验收条件：
  - AC-10-1：输入同一 PSP 参考号，查询同时命中交易参考号或事件参考号对应的所有有权交易；即使该订单超过旧搜索索引交易上限也不漏查，每笔只出现一次。
  - AC-10-2：按渠道、日期、来源应用/礼品卡组合筛选后翻页，在静态数据集上结果无重复遗漏；相同创建时间的交易次序稳定，清空筛选恢复默认列表。
  - AC-10-3：单笔旧 ID 与 token 查询仍返回原记录；未成单交易显示结账关联，应用卸载后的历史交易仍显示可追溯来源信息。
  - AC-10-4：无权限人员查询列表、详情或直接访问深链被拒绝；员工渠道受限时列表、总数及详情不泄露其他渠道数据。
  - AC-10-5：列表加载失败提供重试，零结果显示当前筛选及清空入口；礼品卡详情可定位本卡的扣款/退款交易，不显示其他卡记录或完整卡码。

#### 经营信息与数据处理可靠性

### R11 · 完善经营信息维护与保存反馈

- 来源：Instruction“改善……经营信息维护”；推导依据：Base `SiteSettings` 和 Dashboard `siteSettings` 维护店铺介绍、发件信息及公司地址，前端一次提交包含两个独立 mutation，地址 mutation 的空值具有删除语义。
- 优先级：P0
- 需求描述：在现有设置页统一呈现店铺展示名称、店铺介绍/页头、公司名称及完整经营地址、邮件发件名称/地址、公共和私有 metadata。新增可维护的展示名称不得隐式修改站点域名；公司名称使用 `Address.companyName`。无需新增营业执照、税号认证或独立商家主体系统。API 支持按字段更新，省略保留原值；明确清空与非法空值不同，清空地址必须由用户显式执行。保留现有字段长度、邮箱和按国家校验地址的规则，敏感数据不写公共 metadata。Dashboard 按独立保存区提交信息与地址并分别显示成功/失败，避免多个独立 mutation 被界面说成一次原子保存；未成功字段保留用户输入，重复保存不重复新增地址。现有 API 的已定义 null 清空行为继续保留，新前端不能用“未编辑”触发它。设置变更通知按 R15 处理。
- 验收条件：
  - AC-11-1：有 `MANAGE_SETTINGS` 权限者更新展示名称和介绍，刷新后值一致，域名不变；未传入的其他设置及公司地址保持原值。
  - AC-11-2：仅保存发件信息时不调用地址清空；显式删除经营地址并确认后地址为空，历史订单地址快照不受影响。
  - AC-11-3：输入不合法邮箱、带换行的发件名称或不符合国家规则的地址，对应保存区失败且原值保留，其他成功区域明确显示已保存，不展示整体成功的假象。
  - AC-11-4：无权限者直接修改设置被拒绝；匿名 `shop` 和订阅无私有 metadata 权限的应用无法读取私有字段；合法旧设置升级后仍可展示和编辑。

### R12 · 兼容新旧富文本并安全处理内容

- 来源：Instruction“提升内容处理……可靠性”；推导依据：Dashboard 使用 `@editorjs/list` 2.x；Base `clean_list_item` 按字符串数组处理，`clean_image_item` 写入 `ulr` 而非 `url`，现有测试主要覆盖旧列表。
- 优先级：P0
- 需求描述：商品、分类、集合、页面及富文本属性/翻译等使用公共 EditorJS 清理入口的内容，统一兼容旧列表字符串项和新列表对象项（`content`、嵌套 `items`、元数据），保留层级、顺序、样式和合法文字。空段落、空列表、缺失可选字段、未知块及格式错误应有确定处理：非法结构的新写入返回字段错误并保留旧值；旧库异常内容读取不得导致整页或搜索任务崩溃，展示安全可读取部分并记录可定位告警，未经用户确认不覆盖原文。危险链接、脚本及事件属性需在所有文本、列表、图片 URL/说明和嵌入字段一致清理，真实 `file.url` 被处理，正常 HTTPS 等允许链接保留；具体标签/协议白名单在接口契约列明，不能只匹配一种双引号链接形态。
  纯文本提取按阅读顺序递归包含各层文本，用于搜索而不包含可执行 HTML。前端预览和保存后读取都不得执行危险内容。旧内容不要求全库破坏性重写；需要重建派生纯文本/索引时，保留原文备份及异常清单。
- 验收条件：
  - AC-12-1：分别保存并重新打开旧字符串列表和至少三层嵌套对象列表，文字、顺序、层级和合法链接保持；生成的纯文本包含所有层的可见文字。
  - AC-12-2：列表中有空项、图片无 caption、嵌入块缺可选字段，后续有效块仍被处理，保存/读取/索引均不出现服务端异常。
  - AC-12-3：段落、嵌套列表、图片 `file.url` 及 embed 注入大小写混合、实体编码的危险协议或事件属性，预览与保存后不执行脚本，安全链接不被无故破坏，也不产生错误的 `ulr` 字段。
  - AC-12-4：写入非对象块或字段类型错误时返回定位错误、原内容不变；读取已存在的同类脏数据时页面仍可打开，后台能定位异常对象，不能静默清空其内容。

### R13 · 提高外部图片导入的可靠性与安全性

- 来源：Instruction“提升……外部图片……可靠性”“处理受影响的安全……问题”；推导依据：Base `is_image_url` 依赖后缀，`validate_image_url` 使用 HEAD，产品媒体再以 GET 下载；已有 hardened HTTPClient 和私网过滤应复用。
- 优先级：P0
- 需求描述：通过 URL 导入商品图片时支持带查询参数、无扩展名以及不支持 HEAD 但支持 GET 的合法图片源；以实际下载内容的可解码格式作为最终依据，不能只信文件名或 Content-Type。对已有视频/oEmbed 路径保持支持，不能把任意网页保存为图片。统一处理下载超时、非成功响应、非图片内容、损坏图片、过大字节/像素及不支持格式，返回字段错误，不落下成功媒体记录或无法清理的临时文件。产品默认限制为下载 20 MiB、4000 万像素、总下载预算 20 秒，作为本轮新增验收上限，部署可调但必须有有限边界；本地上传原支持格式不因此减少。首版不自动跟随重定向，3xx 返回可操作错误并提示提供最终直链。
  默认仅允许 HTTP/HTTPS 公网地址，遵守现有生产配置中更严格的策略，阻止回环、私网、链路本地/云元数据地址及 DNS 解析绕过，不能为解决兼容而全局关闭过滤。需要鉴权但未提供公开直链的资源明确失败，不代用户访问内部资源。适用同一外部图片下载路径的应用品牌图等也应复用安全边界。Dashboard 导入过程显示进行中，失败可重试且既有图片不丢失。
- 验收条件：
  - AC-13-1：导入无扩展名但内容为受支持图片的公网 URL，及 HEAD 返回 405、GET 返回合法图片的 URL，成功显示图片和缩略图，原有 JPG/PNG 等直链仍可用。
  - AC-13-2：扩展名为 `.jpg` 而实际为 HTML、伪造 MIME、损坏图片或不支持格式，导入失败并返回可理解错误，没有成功媒体记录。
  - AC-13-3：超过默认字节或像素限制、慢速响应超过总预算、404 或 3xx 响应均在边界内终止；重复失败不会留下孤立文件，原图仍可见。
  - AC-13-4：尝试私网、回环、云元数据地址或将公网域名解析到内网，生产默认配置均拒绝；日志隐藏 URL 中敏感查询参数，不能通过内容检测绕过地址检查。
  - AC-13-5：现有合法视频 URL 仍走原视频展示；图片导入失败后 Dashboard 保留输入供修改并允许重试，不假显示上传成功。

### R14 · 保证搜索结果可用与更新可恢复

- 来源：Instruction“提升……搜索……可靠性”；推导依据：Base 商品、订单、顾客等使用 PostgreSQL 搜索与异步索引；商品存在 `search_index_dirty`，重建命令主要补空索引，富文本结构变化可能影响派生内容。
- 优先级：P0
- 需求描述：本轮覆盖已有商品、订单、顾客、礼品卡搜索及 R10 新交易查询，不新建搜索产品。旧搜索字段、权限与渠道隔离不退化；商品嵌套列表和富文本属性内容能被正确索引，关联属性/页面名称、变体 SKU、顾客信息及交易参考号变动按既有搜索语义更新。空搜索按原列表行为处理，标点、引号、中文及长输入不触发服务端崩溃，不承诺新增语言分词或语义搜索。异步索引允许短暂延迟，标准本地验收环境中单次正常更新提交后 60 秒内可检索新值；这是产品验收目标而非现有生产 SLA。
  索引失败可观测且可重试，任务中断后可继续，异常单条不会使后续对象永久不被处理；全量重建必须覆盖已有非空旧索引，并在过程中保留可用查询能力。并发编辑期间不能将旧快照回写后错误清除较新的待更新状态。维护窗口迁移富文本与礼品卡后执行必要的索引重建，给出处理总数、失败对象及重试结果。后台搜索问题提示不得暴露私有字段。
- 验收条件：
  - AC-14-1：修改商品嵌套列表文字、SKU 或已索引的关联页面名称，标准环境内 60 秒内能用新值命中，不再仅保留旧值；顾客和礼品卡的现有检索场景仍通过。
  - AC-14-2：对空串、仅标点、引号、中文和超长输入发起搜索，返回列表、空结果或明确输入错误，无 500；过滤与渠道权限仍有效。
  - AC-14-3：索引任务暂停期间连续编辑同一对象两次，恢复任务后最终索引反映最后一次提交，不能因处理旧快照丢失新更新。
  - AC-14-4：全量重建中放入一条异常历史内容并中断进程，续跑能完成其他对象，报告异常 ID，修复后可重试；原非空旧索引确实被更新。

#### 应用事件及消费者过渡

### R15 · 补齐可订阅的数据变化事件

- 来源：Instruction“外部应用应能按需接收相关数据变化”；推导依据：Base `webhook/event_types.py` 与 `graphql/meta/extra_methods.py` 已覆盖部分 metadata 对象，但缺少若干经营对象；交易只列有 metadata 更新事件，Shop 普通设置也没有独立更新通知。
- 优先级：P0
- 需求描述：在原有事件之上增加以下业务事件能力，最终枚举名称在契约中锁定，不把建议名当作 Base 已存在字段：
  1. 经营信息普通字段及公司地址变化：`SHOP_UPDATED`；metadata 变化继续使用 `SHOP_METADATA_UPDATED`。
  2. 交易建立与交易金额/状态/退款变化：`TRANSACTION_ITEM_CREATED`、`TRANSACTION_ITEM_UPDATED`，包含平台礼品卡及既有外部交易，metadata 专用事件保留。
  3. metadata 新增、修改、删除：补齐 `Attribute`、`Category`、`Menu`、`MenuItem`、`Page`、`PageType`、`ProductType`、`ShippingMethod` 的对应 metadata 更新事件；现有 Shop、订单、商品、变体、仓库、渠道、礼品卡等保持支持。`AttributeValue` 在 Base 中不具备 metadata，不为补事件而新增其数据模型；其普通变化继续使用现有属性值创建/更新/删除事件。
     事件覆盖通用 metadata mutation、对象创建/更新中内嵌 metadata 和批量写入等实际入口；新对象建立时随创建事件提供初始 metadata，不额外伪造一次“修改”，后续实际修改才发更新。以已提交状态为准，失败/事务回滚不发送，值未变化不产生新的逻辑更新事件。一次业务提交同一对象同类变化只产生一个逻辑事件；网络重试允许重复投递相同事件标识。变更顺序由对象标识、发生时间及可比较版本/序号说明，不要求全局有序。
     每个事件绑定最小领域权限，payload 只给订阅选取且有权读取的字段。私有 metadata 必须经过其原权限校验，不能借公开事件泄露；订单/交易事件遵守渠道权限。员工数据不能因普通顾客事件流被披露。礼品卡全码、凭证和密码永不出现在新增通知里。存量通用更新事件中原有 metadata 触发行为在过渡期保留，并在文档说明可能与专用事件同时出现，消费者按事件类型处理。
- 验收条件：
  - AC-15-1：修改店铺介绍和公司地址分别在提交后收到 `SHOP_UPDATED`，无修改保存不发新事件；仅修改 Shop metadata 时收到其专用事件。
  - AC-15-2：外部或礼品卡交易创建、成功扣款、部分退款分别产生对应交易事件，查询 payload 中金额与已提交账务一致；事务回滚不出现成功变化事件。
  - AC-15-3：对八类补齐对象逐一通过通用 metadata 更新/删除以及其支持的内嵌/批量入口修改，订阅者收到对应事件；批量部分失败只通知成功对象。
  - AC-15-4：同一次提交同时改多个 metadata key，仅出现一次该对象该类逻辑事件；重复写相同值或删除不存在的 key 不产生变化事件。
  - AC-15-5：应用仅订阅公开字段时 payload 无私有字段；无对应领域权限创建订阅或投递时权限已撤销，不能获得数据。重试同一通知使用稳定事件标识，版本信息足以让消费者识别迟到通知。

### R16 · 保持按需订阅、投递可靠性及旧 payload 过渡

- 来源：Instruction“外部应用应能按需接收相关数据变化，存量接入有过渡安排”“提升……应用通知的可靠性”；推导依据：Base 已有 GraphQL subscription 自定义 payload、渠道过滤、固定旧 payload、签名及投递记录，不能以新增事件为由重置已有订阅。
- 优先级：P0
- 需求描述：应用可按事件选择订阅、在支持渠道的事件中限定渠道、用 subscription query 选择最小字段；不强制发送整个对象。新增事件只提供 subscription payload，未带合法 query 的新增事件注册被拒绝；现有事件继续支持现有固定 payload 和自定义 query。旧 Webhook 的事件集合、签名方式、目标 URL、启用状态和字段含义在本轮不自动改变，不要求一次性重装应用。新增字段和事件在 Manifest、创建/更新 Webhook、事件列表、payload 示例及 Dashboard 订阅编辑器中一致可见。创建/修改时校验 query 的事件匹配、字段合法性及权限；失败不得覆盖原有效订阅。
  Dashboard 显示事件、payload 模式、所选渠道、投递记录与迁移提示；有 `MANAGE_APPS` 或既有应用所有者权限者方可管理。支持预览样例 payload 和用隔离样例验证，不把真实资金动作当连接测试。发布提供旧订阅清单、对应新 query 示例、影响说明和切换/恢复步骤；单个 Webhook 可先验证再切换，旧固定 payload 的最终停止时间不在本轮强设。
  异步投递按至少一次语义处理：业务提交后可靠登记待投递事件，进程崩溃不丢失已确认的业务变化；失败按有限重试策略执行，耗尽后可见且可授权重试。提供事件标识、事件时间、来源对象及签名校验说明。禁止把“已排队”当“已送达”，应用停用后不再新投递；重新启用可按明确记录恢复未成功投递，不能无提示重放全部历史。同步请求保持其返回结果语义，重试不得造成重复资金动作。
- 验收条件：
  - AC-16-1：旧固定 payload 和旧 subscription 各一条原样升级，原客户端能解析并验证签名；新增事件订阅只选择 ID 与公开字段时只收到所选业务字段及约定信封字段。
  - AC-16-2：订单事件只订阅渠道 A，渠道 B 的变化不投递；非法字段、错误事件 fragment、越权字段或新增事件缺 query 被拒绝，原 Webhook 可继续正常收取。
  - AC-16-3：接收端先返回 500/超时后恢复，按有界策略重试直至成功，记录每次尝试且稳定事件标识不变；持续失败可见最终失败，授权人工重试产生可审计尝试。
  - AC-16-4：业务提交后在发送前模拟进程重启，恢复后仍能投递该变化；业务回滚无通知；重复投递样例可通过文档中的事件标识完成消费去重。
  - AC-16-5：预览、修改 query 并切换一条旧 Webhook 后，新结构按预期投递；恢复旧配置可继续旧结构，其他订阅不受影响，不向无权限账号展示敏感历史 payload。
  - AC-16-6：应用停用或权限撤回期间不发送未授权数据，恢复后由明确的重试范围处理失败记录；过期/已删除对象事件能依据约定快照或删除标识解析，不因读取不到对象无限重试。

  - AC-18-2：升级前创建的有效、已过期、次数耗尽及无到期链接逐一验证：有效链接可下载原文件并计数，过期/耗尽链接拒绝，无到期权益不被擅自缩短。
  - AC-18-3：导出后核对文件校验和、权益数量、关联订单和剩余次数全部一致；恢复演练可以还原资产关联，不能重复发放权益或重置已用次数。
  - AC-18-4：存在仍调用旧字段的消费者或未交接的已付未履约订单时，预检给出具体阻断清单；接入替代流程后的新数字订单能履约并向消费者提供有效访问方式。
  - AC-18-5：未配置可用新数字履约渠道的商品不能继续接受无法履约的新订单，其他普通商品结账不受影响，已购下载仍可用且不能凭可猜测 ID 读取他人文件。

### R19 · 提供可恢复的升级与完整交付验证

- 来源：Instruction“升级允许维护窗口”“保护存量账号、订单、交易和应用接入……具备恢复及交付后验证安排”“方案须覆盖核心 API 与商家 Dashboard 的配套变化”；推导依据：三仓库分离，平台默认 Dashboard 为浮动镜像且持久化依赖数据库、媒体与异步任务。
- 优先级：P0
- 需求描述：后续设计、开发和 QA 以本 PRD 为验收基线，提供配套前后端设计、完整目标 GraphQL schema/接口说明与 Base 差异清单，标明每个受影响 query、mutation、输入、枚举、错误码、权限、事件及消费者迁移方式。新增字段名/枚举/错误码可在接口设计阶段规范化，但不能改变本 PRD 的业务语义、默认值或减少验收覆盖。新字段以兼容方式加入，明确移除仅限 R17—R18 的退出清单；不得顺便删除其他弃用 API。Dashboard 生成代码及运行调用必须基于同一目标 schema。
  升级采用维护窗口：先生成不含明文密钥的影响报告，验证外部登录/支付/履约路径，备份数据库、媒体、应用配置及必要密钥；停止入口写入、暂停或排空任务，记录支付回调与待投递事件，执行迁移/对账/索引，部署可追溯版本，验证后开放流量。维护期间外部回调必须可持久接收或由已验证的发送方重试，不能吞掉资金结果。API、worker 和 Dashboard 使用与交付源码对应的固定版本/镜像摘要，不能继续用无来源的 `latest` 作为交付证明。
  开放前失败可恢复一致的数据库、媒体、配置和构建版本；开放后已有新订单/外部资金动作则先暂停并对账、保留增量，采用前向修复或可重放恢复，禁止直接回滚旧数据库丢弃新资金事实。必须有恢复责任人、检查步骤、日志和恢复验证结果，具体维护时长/RTO 通过本地演练测定并记录，不虚构生产承诺。交付本地 API 与 Dashboard、必要数据库/缓存/worker，以及可控的身份/支付/运费/Webhook 验证端，不要求建设第三方产品。每条 AC 有验证结果或明确失败原因；所有 P0 场景通过且无未解决的数据/权限/资金阻断项才满足交付条件。
- 验收条件：
  - AC-19-1：对代表性 Base 数据副本执行完整升级，影响清单、迁移映射、按币种账务及库存/账号/应用数量核对有记录；没有静默删除账户、订单、交易、资产或订阅。
  - AC-19-2：本地交付运行的 API、worker、Dashboard 均可关联到本次源码版本及目标 schema，Dashboard 登录、查询、保存和退款流程不出现缺失字段/枚举错误。
  - AC-19-3：在迁移中断与上线前验证失败两处演练恢复，恢复后旧登录、订单读取、卡余额、应用投递及历史下载样本可用，重试迁移没有重复账务。
  - AC-19-4：维护期间模拟支付回调和排队通知，恢复后资金结果不丢失，通知可投递且可去重；上线后新增资金动作场景采用增量对账恢复而非覆盖旧快照。
  - AC-19-5：交付验证记录覆盖三种登录、两种库存、运费缓存及故障、礼品卡混合支付/退款、交易权限、经营信息、富文本、图片安全、搜索、事件过渡及旧能力退出，每条 AC 可定位结果与证据；有 P0 失败则标记未达到验收并进入当前流程允许的有界修复。

## 4. 范围与非目标

本次产品范围包含 R01—R19 的核心 API、Dashboard、必要平台配置、迁移/预检/恢复工具、契约和本地验证要求。优先级按“移除此需求是否导致输入目标无法实现或带来数据/资金/安全错误”评定，因此本轮最小完整范围均为 P0；不是把所有潜在增强都列为必做。本阶段实际交付仅为此 PRD，不在产品阶段实施代码、迁移、部署或修改其他已冻结交付物。

明确不做：

- 不建设顾客 Storefront、原生 App、支付服务商或身份产品；现有消费者由其维护方按契约接入。
- 不建设应用市场结算/商业分成、任意自定义 Dashboard 页面搭建器，首版只补齐 R01 指定详情挂载点。
- 不提供商家自由调整熔断阈值或不受控的同步支付重放；首版使用现有阈值与自动恢复。
- 不新增跨币种兑换、礼品卡转账/提现、储值利息、自动延期、退款自动转现金；不把所有历史 `Payment` 强行转换为新支付来源。
- 不删除未整体弃用的内置支付、邮件、OpenIDConnect、插件扩展框架、普通数字商品或文件属性。
- 不建设语义搜索、推荐系统、独立媒体代理/CDN 或新的数字内容分发产品。
- 不承诺无停机升级；业务输入已允许维护窗口。维护时长与生产容量承诺需以真实环境演练得出。

延期事项：所有旧固定 Webhook payload 的最终停止日期、R01 之外更多挂载位置、熔断阈值自助配置、全局搜索产品和历史数字权益兼容服务最终下线，均不在本轮。原因分别为需消费者迁移证据、缺少具体使用场景、缺少运维量化依据，以及无到期已购权益不能被随意终止。本轮必须提供其所需的清单和迁移说明，不以延期为由拖延已列出的新增能力及明确退出项。
